The Problem

Hundreds of Crates, No One Tracking Them

Every day, factory trucks delivered bread to 11 distribution centers using plastic crates. Crates were supposed to return the same day. Nobody was counting.

👁
Lost Crates Were Invisible
Without a central record, no one could tell which DC was holding the most crates, which driver had stopped returning them, or which day of the week losses were highest.
📊
Inconsistent Formats Across 11 DCs
Each DC used its own Excel format — different column names, date formats (DD/MM/YYYY vs YYYY-MM-DD), delimiters (comma vs semicolon), and time conventions (AM/PM vs 24h). Cross-DC analysis required manual cleanup every time.
⏳
Losses Found Too Late
Shortfalls were only discovered at physical stock counts — always too late to act. There was no alert, no threshold, and no automated detection of data entry errors like “returned more crates than the truck can carry.”
💻
No IT Infrastructure at DCs
Distribution centers had no dedicated server, no DevOps, and no budget for software deployment. Any solution had to work with what was already there: a browser and an internet connection.
✗ Before — Manual Spreadsheets
Each DC maintains its own Excel — different columns, formats, date conventions
Crate losses only discovered at monthly physical stock count
No way to identify which driver or branch is responsible
Data entry errors (truck return capacity exceeded) go unnoticed for weeks

✓ After — Crate Monitoring System
CSV from any DC imported directly — keyword mapping handles all format variants automatically
Anomalies flagged instantly on import — no waiting for month-end
KPI score per branch and leaderboard per truck — accountability visible from day one
4 anomaly categories auto-detected on every import
All 11 DCs on one dashboard — synchronized via Google Sheets
Opens on any device, any time — no installation, no server, no training needed

Core Features

Built Around Real Operational Pain

Each feature maps directly to a problem the ops team faced — not a nice-to-have, but a daily workflow requirement.

01
CSV Import with Column Name Normalization
Reports from each DC arrived in inconsistent formats — different column names, delimiters, date formats, and time conventions. The parser resolves all of it automatically with no configuration required. Typical import: under 500 rows per DC per day — well within client-side parsing limits with no noticeable lag.
Delimiter auto-detected: , vs ; from first row
Column matching via keyword map: “Lambung”, “No Lambung Kirim” → same field
Date normalized: DD/MM/YYYY · YYYY-MM-DD · DD-MM-YY → ISO
Time normalized: 12h AM/PM and 24h → HH:MM

02
Fleet Master — Auto-lookup Truck Capacity
When an operator types a truck number, the system instantly pulls truck type and maximum crate capacity from the internal fleet master. This eliminates manual entry errors and makes the “return exceeds capacity” anomaly check possible — without the operator knowing a capacity table even exists.
Type 645 → DOUBLE, 360 krat capacity — auto-filled
Unknown number? Manual capacity entry → system infers truck type from range
Capacity feeds directly into the “return > capacity” anomaly check

03
KPI Score per Branch (1–10)
Every branch receives a numeric performance score based on the gap between crates sent and returned, relative to truck capacity. Scores are ranked and visualized as an interactive bar chart — clicking any bar drills down into that branch’s detail. Makes accountability visible without manual calculation.
score = max(1, 10 − |%sent − %returned| × 10)
Higher score = smaller gap between sent and returned

04
4-Category Anomaly Detection
The Anomaly tab scans the entire dataset on every import and groups irregularities into four categories — catching both data entry mistakes and real operational issues before they become month-end surprises. Anomalies are informational flags, not automated actions. The ops team confirms each flag via phone or WhatsApp with the driver or DC before taking action — the dashboard surfaces the signal, human judgment makes the call.

Architecture

Zero-Install by Design

The distribution environment had no dedicated server and no DevOps. The architecture was built around that constraint from day one — not retrofitted to it.

🗃
Single HTML File
The entire application — React 18 components, CSV parser, anomaly engine, chart logic — is bundled in one index.html. React loaded via CDN, JSX transpiled in-browser by Babel Standalone. No npm, no build step, no deployment pipeline. Can be opened directly, sent via email, or saved to a USB drive. Known trade-off: Babel Standalone adds parse overhead on first load — acceptable at this scale (<500 rows, desktop environment), but a production rewrite would pre-compile JSX.
React 18 CDN Babel Standalone Zero build step
📈
Google Sheets as Backend
Manual form submissions POST directly to a Google Apps Script endpoint that appends rows to Google Sheets. The same Sheet is used for user authentication — username and password stored as plaintext rows, checked on login. Known limitation: plaintext credentials are acceptable only because this is a closed internal tool with a fixed team of known operators — not suitable for public-facing deployment. The ops team already knows how to open Sheets for data review.
Apps Script Web App POST append API Auth via Sheet (plaintext — internal only)
🔌
Resilient Storage Layer
localStorage can be blocked in private/incognito mode. A safe storage shim detects this and falls back to an in-memory _memStore transparently. If corrupted legacy data causes a crash, an ErrorBoundary catches it and shows a one-click “Reset Application” button that clears cache and reloads.
localStorage shim In-memory fallback ErrorBoundary reset
Known Limitations
Plaintext auth Username and password stored as plaintext in Google Sheets. Acceptable for a closed internal tool with a fixed team, but not suitable for any public-facing deployment. A production version would use hashed credentials or OAuth.
Babel in-browser JSX is transpiled by Babel Standalone in the browser on first load. At <500 rows and a desktop environment this is not a bottleneck, but a production rewrite would pre-compile JSX at build time.
Manual confirmation Anomaly flags require manual confirmation via phone or WhatsApp before any action is taken. There is no in-app dismiss or audit trail for confirmed vs. false positive anomalies.
