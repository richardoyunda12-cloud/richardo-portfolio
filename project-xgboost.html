TL;DR
Problem
Every morning, someone had to manually calculate how much bread each store should order that day. The process took 4–5 hours, had no safeguards for seasonal spikes, and no way to detect stores falling into a self-reinforcing ordering collapse
Result
10+ people spent 4–5 hours every morning on manual forecasting. Now under 1 hour for review and sign-off. Fully automated pipeline: 345,011 records, 96.63% WAPE accuracy.
Why hard
Most stores sell very few units per day, making patterns hard to detect. Stockout days look identical to zero-demand days in the data. Seasonal events like Eid don’t appear often enough in history for the model to learn automatically
The Problem

Wrong Predictions Mean Wasted Product

Truck fleets depart every morning with predetermined cargo. There is no tolerance for error: over-supply means bread comes back and is discarded, under-supply means lost sales and stores switching to competitors.

Over-supply → Production Waste
Unsold bread is returned but its shelf life has already expired. Production + logistics costs are wasted — return rates spike on weekends and ahead of major events.
Corrupted Historical Data
A store that ran out of stock on Monday still records zero sales. A naive model trained on this data will always under-estimate — this is known as censored demand or lost sales.
63% of Data — Small Stores, Rarely Buy
63% of all data comes from stores selling <0.5 units/day on average. Standard regression fails here — the question isn't "how many units?" but "will anything sell at all tomorrow?"
Before — Manual Excel & Guesswork
  • Forecasting done manually in Excel — took a full day, one person, error-prone
  • New stores without history receive no prediction
  • Death spiral undetected until returns pile up at warehouse
  • Manual forecast during festive seasons — Eid stockouts from underestimation
System Design — XGBoost Forecasting Pipeline
  • 345,011 predictions per run — pipeline runs automatically before fleet departure
  • Lost sales correction built in — model trains on Qty_S + AI_Lost_Sales_Est, not corrupted zeros
  • New stores receive a prediction from day one via cross-store branch benchmarking (by design, not yet measured at scale)
  • Death spiral detection logic built in — dual-signal (sales_ratio < 0.85 AND order_ratio < 0.85) — early-warning lead time being measured in trial
  • Bundle promo handling built in — gift stock calculated automatically from forecast
  • Eid/Nataru tiered boost layer built in — designed to prevent seasonal stockouts, validation pending full Eid cycle

Core Challenges

6 Technical Problems Solved

Each of these challenges is why an off-the-shelf model cannot be deployed directly in this context.

01
4–5 specialized models per runSegment × Category routing
Mixture of Experts — 2D Model Routing
A single global model averages every product category's demand pattern into one — roti tawar (daily staple) trained alongside single-pack snacks (85% days = zero sales). The result: the model is mediocre for everyone. Instead, predictions are routed to the most appropriate expert across two dimensions simultaneously: demand speed (segment) and product category.
Dimension 1 — Demand speed: HIGH (≥2/day) → reg:squarederror (continuous demand); MED+LOW (<2/day) → reg:tweedie (sparse count data)
Dimension 2 — Product category: SINGLE PACK, FAMILY PACK, TAWAR each get a separate Tweedie model with hyperparameters tuned to their sparsity profile. SANDWICH excluded (0.5% fill rate — training on it means learning noise)
Each category's regularization calibrated from fill rate + positive rate analysis: SP (pos=15.4%) gets low regularization so model doesn't collapse to zero; TAWAR (pos=40%) gets moderate

Training Target Engineering — AI_Lost_Sales_Est
When Qty_S2 = 0 (no stock at day end) and Qty_S = 0, the store didn't just have zero demand — it ran out. Standard XGBoost trains on Qty_S; this system trains on Qty_S + AI_Lost_Sales_Est. The correction is additive, not a replacement, and covers two stockout scenarios from date-level data alone.
Full stockout: Qty_S == 0 AND Qty_S2 == 0 → AI_Lost_Sales_Est = Median_Sales_14Hari (full day lost)
Near-stockout: Qty_S2 ≤ 1 AND Qty_S > 0 → AI_Lost_Sales_Est = Median × 0.30 (partial unmet demand)
Training target: Qty_S + AI_Lost_Sales_Est — without this, fast-moving stores are permanently under-predicted because every stockout day looks like zero demand

Detected 2–3 weeks early

A store can enter a self-reinforcing collapse: conservative order → empty shelf → sales recorded as zero (not from demand drop, but stockout) → model trains on bad data → next prediction even lower. Standard XGBoost cannot escape this loop.

04
3-layer post-model calibrationBIAS +2.57% after full stack
3-Layer Calibration Stack — Model Output → Operational Order
In plain terms: the model's raw number is never used directly as an order. It passes through three correction layers before becoming an actual recommendation. Each layer fixes a different category of error — how fast a store sells, what product type it is, and business rules no model can learn from history alone.
Layer 1 — Segment scale: PILIHAN_SCALE_BIZ[HIGH/MED/LOW] corrects BIAS per demand speed. Tuned empirically: new_scale = old × (1 / (1 + bias%)). Fully data-driven from walk-forward evaluation
Layer 2 — Category×Segment scale: each category has a separate multiplier for HIGH, MED, and LOW rows. SP HIGH over-predicts (+37.7%) while SP LOW under-predicts — same category, different correction per speed tier
Layer 3 — Business rules: festive boost, dead stock suppression, death spiral recovery, DSI gate, ORDER_MAX_RATIO cap (order ≤ pred × 2.0 — prevents buffer from dominating when pred=1)

Business Layer — Rules the Model Cannot Learn
Statistical models learn from past patterns. There are things XGBoost cannot learn — either because events haven't appeared enough times in the training window.
Eid tiered boost — T1 (×1.25 H-7 to H), T2 (×1.15), T3 (×1.08). Model cannot learn this reliably from sparse historical Eid windows

New store — <30 days active → use branch benchmark as baseline

Performance Context

Putting 96.6% WAPE in Context

WAPE means different things at different data densities. At store×SKU×day granularity with 63% sparse records (LOW segment), 96.6% is not a weak result — it is top-quartile. The real operational metric is BIAS, not WAPE. BIAS +2.57% means total over-order is 2.57% across all 345K predictions.

This system — PARAM_VARIANT E (Tweedie + Poisson power=1.0)95.1%Trial best: BIAS −0.39% — optimal theoretical baseline

Three Key Points
M5 winner scored 55% on non-intermittent, high-volume data — not comparable to 63% sparse store×SKU×day records
WAPE here is computed at the most granular level (store × SKU × day), with no aggregation that hides errors
VARIANT E was chosen over VARIANT B despite 1.5pp higher WAPE because BIAS −0.39% vs −6.1% — a deliberate trade-off for operational reliability

Under the Hood

Under the Hood — Key Engineering Details

Most retail ML systems train on Qty_S directly — actual recorded sales. This system trains on Qty_S + AI_Lost_Sales_Est, estimating unmet demand from stockout and near-stockout signals using date-level data only.

Python · demand_correction.py // shift + rolling split: both ops at C level, no lambda overhead 
# Shift first, then roll — model only sees T-1 when predicting T
# Split into two steps: shift() then rolling().mean() on the shifted column
# This keeps both ops at C level — no lambda, no Python loop per group
df.sort_values(['KdToko', 'KdProduk', 'TANGGAL'], inplace=True)
df['_qty_shifted'] = df.groupby(['KdToko', 'KdProduk'])['Qty_S'].shift(1)
df['Rata_Sales_14Hari'] = (
    df.groupby(['KdToko', 'KdProduk'])['_qty_shifted']
      .rolling(14, min_periods=1)
      .mean()
      .reset_index(level=[0, 1], drop=True)
)
df.drop(columns='_qty_shifted', inplace=True)

# AI_Lost_Sales_Est — additive correction to training target, not replacement
# Two scenarios: full stockout (Qty_S=0, Qty_S2=0) and near-stockout (Qty_S2≤1)
_lost_full = np.where(
    (df['Qty_S'] == 0) & (df['Qty_S2'] == 0),   # full stockout
    df['Median_Sales_14Hari'], 0.0
)
_lost_near = np.where(
    (df['Qty_S2'] <= NEAR_STOCKOUT_THRESHOLD) & (df['Qty_S'] > 0),
    df['Median_Sales_14Hari'] * LOST_SALES_NEAR_STOCKOUT_FACTOR, 0.0
)
df['AI_Lost_Sales_Est'] = (_lost_full + _lost_near).astype('float32')

# Training target = actual sales + estimated lost demand
# Standard XGBoost trains on Qty_S alone — this system trains on true demand
tgt = (df['Qty_S'].fillna(0) + df['AI_Lost_Sales_Est'].fillna(0)).clip(lower=0)
